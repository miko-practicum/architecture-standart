| Код | Требования | Комментарий |
|-----|------------|-------------|
| F | Функциональные (Functionality) | |
| | На сайте должен отображаться список доступных депозитов с актуальными ставками. | Требование влияет на источник данных по ставкам: текущие XLS-файлы не подходят для онлайн-канала. Нужен управляемый источник данных или сервис ставок. |
| | Новый клиент должен иметь возможность подать заявку на депозит на сайте, указав Ф. И. О. и номер телефона. | В MVP сайт не открывает депозит, а создаёт лид/заявку для дальнейшей обработки кол-центром. |
| | Заявка с сайта должна попадать в систему кол-центра или быть доступна менеджеру кол-центра для обработки. | Это архитектурно значимая интеграция между сайтом и системой кол-центра. Сейчас такая интеграция для депозитных заявок не описана. |
| | Менеджер кол-центра должен видеть заявку с сайта и иметь возможность предложить клиенту специальные условия. | Для специальных условий нужны данные о ставках и правилах, но без раскрытия лишних данных между депозитным и кредитным направлениями. |
| | Новый клиент после заявки на сайте должен пройти идентификацию в отделении. | Это ограничение MVP: банк не может открыть депозит новому клиенту полностью онлайн без личной проверки документов. |
| | В интернет-банке действующий клиент должен видеть список доступных депозитов с актуальными ставками. | Интернет-банк должен получать ставки из нового/целевого источника, а не из ручных XLS-файлов. |
| | В интернет-банке действующий клиент должен видеть персонализированные ставки. | Требование влияет на интеграцию с АБС и правила расчёта ставок. Желательно не давать интернет-банку прямой доступ к АБС. |
| | Действующий клиент должен иметь возможность подать в интернет-банке заявку на открытие депозита, указав счёт списания и сумму депозита. | Для MVP заявка обрабатывается бэк-офисом, но клиентский путь должен быть цифровым. |
| | Подача заявки в интернет-банке должна подтверждаться SMS-кодом. | Функционал SMS есть в ядре интернет-банка и требует доработки подрядчиком. Желательно реализовать подтверждение силами команды банка без изменения ядра, если это возможно. |
| | Бэк-офис депозитов должен обрабатывать заявки на открытие депозита в АБС и подтверждать условия депозита. | Это сохраняет текущую операционную модель MVP и снижает объём изменений на первом этапе. |
| | Сотрудники бэк-офиса депозитов и кредитов должны иметь возможность работать со ставками без обмена XLS-файлами по почте. | Требование устраняет ключевое узкое место: ручной расчёт и ежедневный обмен Excel. |
| | После подтверждения ставки клиент должен получать SMS-уведомление. | Уведомление нужно как для заявок после звонка, так и для заявок из интернет-банка. |
| | После открытия депозита клиент должен получать SMS-уведомление. | Это часть клиентского информирования и контроля статуса операции. |
| | Необходимо вести статусы заявки на депозит: создана, в обработке, ставка подтверждена, депозит открыт, отказ/ошибка. | Дополнительное требование. Статусы нужны для поддержки клиента, аудита и последующего развития процесса до полностью автоматического открытия. |
| | Необходимо хранить историю действий по заявке и решения по ставке. | Дополнительное требование. Для банка важны аудит, разбор спорных ситуаций и контроль действий сотрудников. |
| U | Удобство использования (Usability) | |
| | Интерфейс подачи заявки на сайте и в интернет-банке должен быть максимально простым и понятным клиенту. | Банк хочет привлечь более молодую аудиторию, но текущая клиентская база старшего возраста тоже должна справляться с интерфейсом. |
| | Клиент должен видеть привычные цвета, брендированные элементы и компоненты дизайн-системы банка. | Требование прямо указано бизнесом и влияет на фронтенд сайта и интернет-банка. |
| | В интернет-банке клиент должен видеть персонализированные условия до отправки заявки. | Это снижает количество обращений в кол-центр и отделения. |
| | Клиент должен получать понятный результат после отправки заявки: заявка принята, ожидайте подтверждение или звонок. | Дополнительное требование. Без явного результата клиент будет повторно звонить или создавать дубли заявок. |
| | Для сайта форма заявки должна запрашивать только минимально необходимые данные. | Уменьшает трение и снижает объём чувствительных данных, передаваемых с сайта. |
| | Ошибки при отправке заявки и подтверждении SMS-кодом должны отображаться понятным текстом без технических деталей. | Важно для клиентского опыта и безопасности. |
| R | Надёжность (Reliability) | |
| | Сервисы нового депозитного процесса должны быть доступны 24/7 с целевым уровнем доступности 99,9%. | Требование задано бизнесом и IT. Оно влияет на размещение, резервирование и мониторинг. |
| | Интернет-банк и связанные сервисы должны сохранять доступность при сбое основного ЦОД. | Сейчас интернет-банк фактически работает в одном ЦОД на одной группе серверов, переключение на резервный ЦОД есть, но требования пока невыполнимы. |
| | Новый процесс не должен создавать критическую нагрузку на базу данных АБС. | Команда АБС сообщает, что БД уже перегружена. Прямая онлайн-нагрузка от заявок может угрожать работоспособности банка. |
| | Для нового процесса нужно избегать прямой работы интернет-банка с API или БД АБС. | Требование снижает связность и защищает АБС от пиков онлайн-канала. |
| | Заявки на депозит не должны теряться при временной недоступности АБС или системы кол-центра. | Дополнительное требование. Нужны надёжная фиксация заявки, повторная отправка или очередь/буферизация. |
| | Отправка SMS должна быть отказоустойчивой: при временной ошибке должен быть повтор или понятный статус ошибки. | SMS используется для подтверждения операции и уведомлений, поэтому сбои критичны для процесса. |
| | Должен быть мониторинг доступности и ошибок по сайту, интернет-банку, сервису заявок, интеграциям с АБС, кол-центром и SMS-шлюзом. | Дополнительное требование. Без мониторинга невозможно подтвердить 99,9% доступности и быстро устранять сбои. |
| P | Производительность (Performance) | |
| | Отклик клиентских операций на сайте и в интернет-банке должен занимать миллисекунды. | Бизнес ожидает быстрый интерфейс. Точные SLO лучше уточнить, но архитектурно нужен быстрый ответ пользователю. |
| | Справочные данные, включая список депозитов и ставки, должны загружаться быстрее 1 секунды. | Сейчас некоторые справочные данные при платежах загружаются больше секунды; это известная проблема, которую хотят исправить. |
| | Система должна поддерживать горизонтальное масштабирование клиентских и промежуточных сервисов. | Нужно выдерживать рост онлайн-заявок и распределять запросы между серверами, приложениями и ЦОД. |
| | Нагрузку на АБС нужно ограничивать и контролировать, поскольку АБС масштабируется только вертикально. | Архитектурно важно вынести чтение ставок и приём заявок из прямого синхронного контура АБС. |
| | Чтение актуальных ставок для сайта и интернет-банка должно выполняться из быстрого источника, не из XLS и не через тяжёлые запросы к АБС. | Дополнительное требование. Иначе публичный сайт и интернет-банк будут зависеть от ручного файла или перегруженной АБС. |
| | Подача заявки должна быстро возвращать клиенту подтверждение приёма, а дальнейшая обработка может выполняться асинхронно. | Подходит для MVP, где решение всё равно принимает бэк-офис. |
| S | Поддерживаемость (Supportability) | |
| | При доработках нужно максимально использовать технологии, уже применяемые в банке: MS SQL, Oracle, .NET, Java, React, PHP. | Это снижает стоимость сопровождения и соответствует ограничению из задания. |
| | Новые технологии допускаются только при совместимости с существующими платформами разработки и наличии экспертизы внутри банка. | В банке есть Java-экспертиза в команде АБС и опыт сопровождения систем на .NET, PHP, React. |
| | Если потребуется брокер сообщений, предпочтительно рассматривать Kafka как перспективную технологию. | При этом текущая версия интернет-банка несовместима с Kafka, поэтому нужна прослойка или ограниченное применение вне ядра интернет-банка. |
| | Нужно предусмотреть документацию для дальнейшего расширения депозитного процесса и подключения новых продуктов. | Прямое требование задания. В дальнейшем планируются кредиты и полная автоматизация открытия депозитов. |
| | Новые интеграции должны иметь описанные API-контракты, форматы сообщений, коды ошибок и правила повторной обработки. | Дополнительное требование. Это важно при взаимодействии сайта, интернет-банка, АБС, кол-центра и SMS-шлюза. |
| | Решение должно минимизировать изменения в ядре интернет-банка, зависящие от подрядчика. | Доработка SMS в ядре требует участия подрядчика, чего бизнес и IT хотят избежать. |
| | Логика ставок должна быть вынесена из XLS-файлов в сопровождаемую систему с разграничением прав доступа. | Это влияет на поддержку, аудит и безопасность. Возможное место реализации — АБС или отдельный сервис ставок. |
| | Архитектура MVP должна допускать дальнейший переход к микросервисному контуру для депозитов. | В задании предложено рассмотреть микросервисную архитектуру в рамках открытия депозитов, не переписывая весь интернет-банк сразу. |
| +R | + Ограничения (Restrictions) | |
| | Передача чувствительных данных с сайта должна быть защищена шифрованием трафика. | Минимум HTTPS/TLS для сайта и всех внешних клиентских соединений. |
| | Передача данных в интернет-банке должна быть защищена шифрованием трафика. | Требование безопасности для клиентских персональных и финансовых данных. |
| | Доступ сотрудников депозитного и кредитного бэк-офиса к данным друг друга должен быть ограничен. | Это текущее требование безопасности, из-за которого процесс сейчас построен через обмен данными. Новое решение должно сохранить разделение прав. |
| | Новые клиенты не могут открыть депозит полностью онлайн без личной идентификации документов. | Юридическое/регуляторное ограничение для сайта и MVP. |
| | Интернет-банк сейчас является монолитом на ASP.NET MVC 4.5/.NET Framework 4.5 и MS SQL, ядро зависит от подрядчика. | Ограничивает варианты реализации и усложняет внедрение новых технологий вроде Kafka напрямую. |
| | АБС реализована на Delphi + Oracle, основная логика находится в PL-SQL. | Ограничивает масштабирование и определяет способ интеграции с текущими банковскими данными. |
| | База данных АБС перегружена, поэтому новые онлайн-сервисы не должны создавать на неё неконтролируемую нагрузку. | Критичное архитектурное ограничение. |
| | АБС может масштабироваться только вертикально из-за своей базы данных. | Нужно учитывать при расчёте нагрузки и выборе синхронных/асинхронных интеграций. |
| | Система кол-центра является платформой подрядчика, но развёрнута в инфраструктуре банка и допускает расширения. | Для MVP можно использовать её как точку обработки заявок с сайта, но изменения должны учитывать участие подрядчика и возможности расширения. |
| | Партнёрский кол-центр использует внешнюю систему, отличную от системы кол-центра банка. | Если заявки будут передаваться партнёру, потребуется отдельная интеграция или регламент обмена, но в MVP лучше ограничить контур внутренним кол-центром. |
| | Решение должно учитывать наличие основного и резервного ЦОД и необходимость распределения нагрузки между ними. | Требование влияет на инфраструктуру интернет-банка и новых сервисов заявок. |
